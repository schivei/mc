# M41.5 — a module can participate in a function's parameter list

A follow-up in the style of M21.5 and M39.5: one gap a real consumer hit, closed with the
smallest generic mechanism that closes it, and nothing else.

## 1. What was missing

`parse_params` (`src/parse.mc`) accepted exactly one shape, `type name`, and it was the **only
position on the parse path with no hook at all**:

* `parse_top` consults `syntax_find` on the declaration's **first** token, so a `syntax` handler
  either owns the whole declaration or sees nothing of it;
* `word_add` refuses the core type words (`cannot redefine core keyword`), so no keyed table —
  `syntax`, `syntax_stmt`, `syntax_expr`, `syntax_infix`, `type_alias`, `type_new` — can ever be
  reached from `i64`;
* `on_stmt`/`on_jump` run **after** a node exists and cannot consume tokens;
* `syntax_lit` is the numeric-literal position and nothing else.

The consumer is the `ngen` port of the teko language, written against `docs/` against an
unmodified compiler. It is blocked on two things it wants to spell with `mc`'s own function
syntax, and both are parameters:

```c
i64 f(i64 x, i64 y = 10)     // a default parameter
i64 g(params i64 xs)         // a C#-style typed variadic
```

## 2. The decision

The owner chose the hook over the features. `mc` does **not** grow default parameters and does
**not** grow variadics; it grows the one registration that lets a module have them, the same way
`unless`, `class`, `1.5` and `rbit` are not in the language either.

## 3. `syntax_param(&f)`

Registration in `src/hooks.mc`, shaped like `on_stmt`'s: a growable arena block (`grow`), an
arena tag in the `T_*` registry (`T_SYNPARAM`, inserted after `T_ONJUMP`), a linear table walked
in registration order — `docs/determinism.md`, rule 1.

Contract:

```c
i64 f()      // -> the node index of an N_PARAM, or 0 = "the core handles this one"
```

**Where it is consulted, and why there.** At the head of `parse_params`'s loop, right after the
`K_RPAR` test and **before `type_of_token`**. That placement is the whole point:

* a parameter that opens with a word the module taught (`params i64 xs`) must reach the handler
  before the core demands a type — after `type_of_token` it is already `type expected in
  parameter`;
* a parameter that wants a trailer (`i64 y = 10`) must be read as a **whole** by whoever records
  the trailer: `p_type()`, `p_ident()`, then `p_accept(K_ASSIGN)` and `parse_expr(0)` for what the
  module keeps privately. A hook placed after the core had read `type name` would arrive with the
  `=` still unread and no way to attach it to anything.

Handlers run in registration order and the first non-zero answer wins. With none registered
(`nsynp == 0`) the branch is not taken and not even the `callp` happens — the same short-circuit
`nonstmt`, `nonjump` and `nonlit` have.

**The name.** `syntax_param`, not `on_param`: the `on_*` family runs after a node exists and
cannot consume tokens, which is exactly what a default parameter has to do. This is a syntax hook
that may own the parameter, like `syntax_stmt` and `syntax_lit`.

**Two guards**, both raised at the parameter's own position:

| message | when |
|---|---|
| `syntax_param handler consumed no tokens: <word>` | the handler returned a node without advancing; `parse_params` would offer it the same token forever. The `stmt_syntax` precedent, cursor **and** token start compared |
| `syntax_param handler did not return a parameter` | what came back is not an `N_PARAM` (index out of range included). That node goes straight into a list `gen_lower` walks by `nd_type`/`nd_name`: anything else is a wrong frame layout later, not a diagnostic here |

The `MAXPARAMS` count and the `at most 12 parameters` diagnostic apply to what the handler returns
exactly as they apply to what the core reads — the counting is outside the `if`.

## 4. `p_decl_name()`

`uptr p_decl_name()` — the name of the top-level declaration currently being parsed, 0 outside
one. `parse_top` and `parse_extern` set it the moment the name is read (so it is already there
when `parse_params` runs) and `top_add` clears it when the declaration reaches the unit.

A handler needs it to know **which function** the parameter belongs to; without it a module could
record a per-parameter fact and never say whose it was. `lib/user_syntax_demo.mc` keys its default
table by it, which is what makes `i64 f(i64 x, i64 y = 10)` and `i64 g(i64 x, i64 y = 30)` — two
declarations differing only in a default at the same parameter index — come out right.

The pointer is the one `cur_name()` made for that declaration and does not move while the
declaration is read, so identity is a valid comparison and a handler can use it to notice that a
new parameter list has started.

## 5. Acceptance

1. **A default parameter, end to end.** `i64 f(i64 x, i64 y = 10)` spelled in the taught
   compiler; the module records the default from the handler and completes `f(1)` from a `pass()`
   with `decl_find`/`decl_nparams`. Exit 42.
2. **A `params`-style parameter** that opens with a taught word and lowers to `uptr` — the proof
   that the handler saw the word before `type_of_token` did.
3. **`p_decl_name()` observed from inside the handler**, with teeth: two functions differing only
   in the default at the same index.
4. **The two guards**, each a `tests/err/` case with its exact message and a fixture handler in
   `lib/user_syntax_demo.mc`.
5. **Inertness.** With no `syntax_param` registered, `--dump-ast` and every object over `tests/`
   are byte-identical to the frozen seed's (`check-obj` 32/32); and a module whose *only*
   registration is `syntax_param` and whose handler answers 0 for every parameter
   (`lib/user_param_nop.mc`) produces byte-identical trees and objects too.
6. `stage0/` untouched; `make check` RC 0.

## 6. Implementation notes and deviations

* **`cur_decl`, not `decl_name`, is the global.** `src/parse.mc` already has a function
  `uptr decl_name(uptr msg)` — the reader of a name in a declaration, `#rule` holes included — so
  the storage behind `p_decl_name()` is named `cur_decl`, next to `cur_sect` and `cur_dylib`.
* **`parse_extern` sets it too**, which the architect's design named only `parse_top` for. An
  `extern` is a top-level declaration and it calls `parse_params`; leaving it out would have made
  the documented contract ("the top-level declaration currently being parsed") false for exactly
  the declarations an FFI module cares about. One line.
* **The two guards live in `parse.mc`, not in `hooks.mc`.** `run_syntax_param` is the plain walk
  of the table, like `run_syntax_lit`; the guards need `cp`, `tok_start`, `nnodes` and `nd_kind`,
  all of which are the parser's and the AST's.
* **The second guard uses `err_at`, not `err_at2`.** By the time it fires the handler has consumed
  tokens, so `cur_name()` would name whatever token happens to be current — misleading. The
  position it reports is the parameter's first token, which is the useful one. The first guard
  keeps `err_at2` with `cur_name()`, which there *is* the word, since nothing advanced.
* **The demo handler claims every ordinary parameter** and declines only on a non-type token and
  on `void`, so the core keeps `type expected in parameter` and `parameter of type void` word for
  word in the taught compiler as well.
* **`param_new` puts the current token's line on the node**, so a parameter the demo builds
  carries the line of the token after the name rather than of the type. Nothing prints an
  `N_PARAM`'s line (`dump_ast` prints kind, type, name and val), and the demo uses the documented
  API on purpose; a module that wants the exact core line builds the node with
  `node_new(N_PARAM, line, fl)` itself.
* **`T_SYNPARAM` renumbers the tags after it** (`T_BACKENDS`..`T_COUNT`, 38 -> 39). Every use in
  `src/` is symbolic; the visible effect is one more row in `mc limits`, named `syntax_param`,
  between `on_jump` and `backends`.
