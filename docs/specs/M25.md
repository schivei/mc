# Spec M25 — sysroots and cross-compilation resolution

Owner's direction (2026-09-03): cross-compiling must not require the developer to hunt for files.
Apple: the linker's text description of libSystem can be served by `mc`. Linux: musl `libc.a`.
Windows: mingw-w64 import libraries (`*.lib`/`lib*.a`). When the target is the running OS, `mc` uses
what the system already has. Depends on M14 (driver/TOML) and M16 (Linux target); Windows parts on
M19/M20.

## Resolution order for `[target] os/arch` (driver)
1. `[sysroot].path` in `mc.toml` (explicit) — used as-is; missing files are reported by name.
2. Host == target: use the running system.
   - macOS: `--exe` needs nothing. For the `[linker]` path, `{sdk}` = `xcrun --show-sdk-path` when
     Xcode/CLT exist; otherwise `mc` synthesizes the text stubs (below) and links against them.
   - Linux (future host): `/usr/lib/libc.a` + `crt1.o crti.o crtn.o` from the running musl system
     (Alpine layout), else the cache.
   - Windows (future host): `%MC_SYSROOT%` or the cache.
3. Cache: `~/.mc/sysroots/<os>-<arch>/` (override with `MC_SYSROOT_DIR`).
4. Otherwise: a precise error naming the target and printing the exact `mc sysroot fetch <os>-<arch>`
   command plus the manual download instructions (URLs, expected SHA-256, files to place where).

## Apple: two ways, neither redistributes SDK files
1. **Synthesized text stubs (default, no download).** `mc` embeds a TBD v4 template
   (`<sysroot/macos/tbd-template>`) and, at link time, writes `build/stubs/<lib>.tbd` for
   `libSystem.B` and every `[libs]` entry, listing exactly the symbols the program declares `extern`
   for that library (from `[externs]` / `#dylib`), the `install-name` and the target (`arm64-macos`).
   `ld` and `ld64.lld` accept such stubs; `{libs}` expands to them when no SDK is available. Symbol
   names are not SDK content. Sufficient for any `mc` program.
2. **Community SDK mirrors (owner, 2026-09-03): same tactic as Linux/Windows.** `mc sysroot fetch
   macos-aarch64|macos-x86_64` points at community repositories that publish the SDK's `.tbd` set
   (sources listed with URL + SHA-256 in `docs/sysroots.md` and `<sysroot/sources.toml>`; e.g. the
   `MacOSX*.sdk.tar.xz` mirrors on GitHub), downloads with confirmation, extracts only `usr/lib/*.tbd`
   (plus `System/Library/Frameworks/*.tbd` on request) into `~/.mc/sysroots/macos-<arch>/`, and
   prints the `mc.toml` lines to use it:
   ```toml
   [sysroot]  path = "~/.mc/sysroots/macos-aarch64"     # {sdk} resolves here when xcrun is absent
   ```
   Useful when linking third-party objects or libraries whose symbols `mc` does not declare. Offline:
   manual instructions, exit 2. `mc` itself never ships or embeds any file from these mirrors.
- The `--exe` backend keeps binding by ordinal without any stub or SDK.

## Linux: musl
- Cache layout: `~/.mc/sysroots/linux-<arch>/{crt1.o,crti.o,crtn.o,libc.a}` (+ optional
  `libsqlite3.a` and other static libs the developer drops there).
- `mc sysroot fetch linux-aarch64|linux-x86_64`: prints the plan (URL, size, SHA-256, destination),
  asks for confirmation on a TTY (or `--yes`), then runs `curl -L` + extraction (`tar`, present on
  macOS and Linux) into the cache. Sources, in order of preference: Alpine `musl-dev` `.apk` from the
  official CDN (small, versioned, checksummed by the apk index) — `mc` extracts only `usr/lib/{crt*.o,
  libc.a}`; fallback: musl.cc prebuilt toolchains (large). The list of sources with checksums lives in
  `docs/sysroots.md` and in the bundle (`<sysroot/sources.toml>`), so the binary alone knows them.
- Without network: the same command prints the manual steps and exits 2.
- Docker remains the CI/test path (`scripts/sysroot-linux.sh`), unchanged.

## Windows: mingw-w64 import libraries
- Cache layout: `~/.mc/sysroots/windows-<arch>/lib/{libkernel32.a,libmsvcrt.a,...}` (mingw naming;
  `lld-link`/`ld.lld -m aarch64pe|i386pep` accept them).
- `mc sysroot fetch windows-aarch64|windows-x86_64`: from llvm-mingw releases (GitHub), extracting only
  `<triple>/lib/*.a`; checksum verified; manual instructions when offline. `crt` objects for a
  no-CRT `mainCRTStartup` shim are provided by `<sys/windows>` (M19) so only import libs are needed.

## Driver integration
- Placeholders: `{sysroot}` (resolved dir), `{stubs}` (synthesized tbd dir on macOS), `{libs}`.
- `mc sysroot list` shows every target with its resolution (explicit / system / cache / missing).
- `mc build` prints the resolved sysroot on the first line when it is not the system one.

## Acceptance
- macOS without `xcrun` (simulate with `PATH` lacking it and `MC_NO_SDK=1`): a program using `write`
  and `sqlite3_open` links with `ld64.lld` against synthesized stubs and runs; with
  `mc sysroot fetch macos-aarch64 --yes` into a temp cache, the same program links against the fetched
  `.tbd` set through `{sdk}`, and `mc sysroot list` shows the cache as the resolution.
- `mc sysroot fetch linux-aarch64 --yes` in a temp `MC_SYSROOT_DIR`: files present with the expected
  SHA-256; `mc build` for linux then works without `[sysroot].path`; `test-linux.sh` uses the cache
  when Docker's sysroot script is disabled.
- Offline: `fetch` prints the manual instructions and exits 2; `mc build` for a missing sysroot exits 1
  with the same instructions.
- `mc sysroot list` output is deterministic; docs `docs/sysroots.md` complete for the three OSes.
