# Spec M23 — self-adapting limits: growable tables, `[limits]` in `mc.toml`, `mc limits` checker

Owner's direction (2026-09-03): the developer must be able to build safely without ever hitting a
hard-coded table size; `mc` adapts, the TOML can grant headroom, and a checker reports (and, when
allowed, raises) the limits.

## Problem
Every table in the compiler (`nodes`, tokens, defines, strings, globals, functions, rules, syntax
hooks, aliases, dylibs, TOML entries, bundle index...) is a static array sized by a `MAX*` constant.
Programs or taught compilers that grow past one die with `too many X`. The architect had to bump five
constants by hand after M15 (`mc.mc` was at 501/512 strings against the seed).

## Design (all in `src/*.mc`; stage0 keeps its static tables and only ever compiles `src/mc.mc`)
1. **Growable tables.** Every `MAX*`-sized array in `src/` becomes an arena-allocated block that
   doubles on demand (`grow(ptr, count, cap, elem_size)` in `arena.mc`, the pattern `nodes_grow`
   already uses). The `MAX*` names survive as **soft caps**: exceeding a cap is still an error, but
   the cap is data, not array size.
2. **`[limits]` in `mc.toml`** (all optional):
   ```toml
   [limits]
   heap      = "64M"      # compiler arena for this build (mmap'd at startup; default 32M)
   functions = 4096       # soft caps; default = today's constants
   strings   = 4096
   defines   = 4096
   tokens    = 4096
   nodes     = 262144
   ```
   Caps below the current usage of the compiler itself are refused with a message.
   The arena becomes `mmap`-based (libSystem `mmap`, or `svc` in `sys_svc.mc`) so `heap` is honored
   without rebuilding `mc`; the static `heap[]` stays as the fallback when no TOML is used.
3. **`mc limits [DIR]`** (also `mc build --limits`): compiles the project (and the taught compiler,
   if any) and prints one line per table: name, used, cap, percentage, and a verdict
   (`ok` / `near` at >= 80% / `over`). Exit 0 when every table is `ok`, 3 when any is `near`, 1 on
   `over`. Deterministic output, suitable for CI.
4. **`mc build --fix-limits`**: with the developer's consent (the flag), rewrites `[limits]` in the
   project's `mc.toml` so that every `near`/`over` table gets `cap = next power of two >= 2 x used`,
   preserving the rest of the file byte for byte (append or replace the `[limits]` section only),
   and prints what changed. Without the flag, `near`/`over` are reported and nothing is written.
5. **The seed's limits are checked by the build itself:** `make check` gains `check-limits` running
   `mc limits` on `src/mc.mc` and failing when any table of the seed (`stage0/*.c` constants) is
   `near` — this is the early warning the architect lacked at M15.

## Acceptance
- Growth: a generated program with 5 000 functions and 5 000 string literals compiles with default
  caps raised in TOML and with no code change; `make check` objects and golden unchanged for the
  corpus (growth only kicks in above the old sizes) except the one rewrite for the arena change.
- `mc limits examples/api` prints the table; forcing a tiny cap in a temp TOML yields `over` and exit 1;
  `--fix-limits` rewrites only `[limits]` (diff shows nothing else) and the next build passes.
- `check-limits` in `make check` reports the seed headroom (functions, strings, defines, tokens).
- Docs: `docs/build.md` § limits; `docs/determinism.md` note (growth does not change output order).
